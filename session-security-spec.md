# ТЕХНИЧЕСКОЕ ЗАДАНИЕ И МОДЕЛЬ УГРОЗ: Аутентификация на JWT

---

# ЧАСТЬ 1: ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## 1. Цель
Реализовать stateless-механизм аутентификации на основе JWT (JSON Web Tokens), обеспечивающий защиту от XSS (через HttpOnly Cookie), поддержку автоматического обновления сессий (Refresh Token) и безопасный выход из системы (через Blacklist отозванных токенов).

## 2. Функциональные требования

### 2.1. Генерация и доставка токенов
Система использует два типа токенов для баланса между безопасностью и удобством пользователя:
*   **Access Token (Токен доступа):**
    *   **Момент генерации:** Создается после успешной проверки логина и хеша пароля.
    *   **Формат:** JWT, подписанный алгоритмом `HS256`. Секретный ключ подписи хранится в переменных окружения (`.env`).
    *   **Время жизни:** Короткое (15 минут).
    *   **Назначение:** Передается при каждом запросе к API для доступа к защищенным ресурсам.
*   **Refresh Token (Токен обновления):**
    *   **Момент генерации:** Создается одновременно с Access Token.
    *   **Формат:** Криптостойкая случайная строка (не JWT).
    *   **Время жизни:** Долгое (7 дней).
    *   **Назначение:** Используется исключительно для получения нового Access Token без повторного ввода пароля.
*   **Доставка клиенту:** Оба токена передаются через заголовок `Set-Cookie` в разных куках (например, `access_token` и `refresh_token`).
*   **Атрибуты Cookie:** `HttpOnly` (обязательно), `Secure` (для production), `SameSite=Strict` (для production), `Path=/`.

### 2.2. Валидация Access Token (Stateless)
Каждый защищённый эндпоинт выполняет следующие шаги:
1.  Извлекает Access Token из Cookie.
2.  Проверяет криптографическую подпись (HS256).
3.  Проверяет срок действия (`exp > now`).
4.  Проверяет наличие токена в Blacklist.
5.  Если проверки пройдены — предоставляет доступ (извлекает `sub` из Payload).

### 2.3. Автоматическое обновление токена (Refresh Flow)
*   Если Access Token истек, сервер возвращает ошибку `401 Unauthorized`.
*   **Клиентская логика:** При получении 401 клиент автоматически (скрытно от пользователя) отправляет запрос на эндпоинт `POST /refresh`, прикрепляя Refresh Token.
*   **Серверная логика (эндпоинт /refresh):** Сервер проверяет Refresh Token в БД (не истек ли, не отозван ли). Если валиден — генерирует **новую пару** токенов (Access и Refresh) и отправляет их в Cookie. Пользователь продолжает работу, не замечая перерыва.

### 2.4. Инвалидация (Logout) и Blacklist
*   При вызове `POST /logout` сервер добавляет **криптостойкий хеш (SHA-256)** текущего Access Token в таблицу `token_blacklist` в БД SQLite.
*   Refresh Token удаляется из БД.
*   Сервер возвращает `Set-Cookie` с пустыми значениями и `Max-Age=0` для очистки кук.

### 2.5. Хранение
*   **Blacklist (SQLite):** Таблица `token_blacklist` (token_hash, expires_at).
*   **Refresh Tokens (SQLite):** Таблица `refresh_tokens` (token_hash, user_login, expires_at).

## 3. Требования к клиентской части
*   Клиент **не хранит** токены в `localStorage` или `sessionStorage`.
*   Клиент **не передаёт** заголовок `Authorization` вручную.
*   Все запросы к API используют `fetch(..., { credentials: 'include' })`.
*   Клиент реализует перехватчик (interceptor) ошибок `401` для автоматического вызова `/refresh`.

## 4. Особенности локального развертывания (Лабораторная среда)
На этапе тестирования на `localhost` по HTTP без SSL-сертификатов в коде применяются следующие временные конфигурации:
1.  **Флаги Cookie:** Флаги `SameSite=Strict` и `Secure` временно отключены (иначе браузер блокирует куки по HTTP). В production обязательны.
2.  **Секретный ключ:** Ключ `JWT_SECRET` вынесен в код для удобства проверки. В production — в `.env`.

## 5. Архитектура хранения данных
Для обеспечения безопасности и работоспособности системы данные распределены следующим образом:
*   **Клиент (Браузер):** Только `HttpOnly Cookie` с Access и Refresh токенами. Прямой доступ из JavaScript к ним заблокирован.
*   **Сервер (Оперативная память):** Хранятся только счетчики Rate Limiting (попытки входа по логину и IP) и кэш использованных `nonce` (для защиты от replay-атак). При перезапуске сервера эти данные сбрасываются.
*   **Сервер (База данных SQLite):**
    *   `users` — логины, хеши паролей, соли.
    *   `token_blacklist` — хеши (SHA-256) отозванных Access Token.
    *   `refresh_tokens` — хеши (SHA-256) активных Refresh Token (для возможности их отзыва при Logout).

# ЧАСТЬ 2: МОДЕЛЬ УГРОЗ

## 1. Активы
*   **Access Token:** Дает краткосрочный доступ к аккаунту.
*   **Refresh Token:** Позволяет получить новый Access Token. Его кража дает долгосрочный доступ.
*   **Секретный ключ подписи (JWT_SECRET):** Компрометация ключа позволит злоумышленнику генерировать любые Access Token.

## 2. От чего система ЗАЩИЩЕНА (Реализованные меры)

### Угроза 1: Подделка токена (JWT Tampering)
*   **Сценарий:** Злоумышленник меняет `sub` (логин) в Payload или подделывает подпись.
*   **Мера защиты:** Использование алгоритма `HS256` и строгая проверка подписи. Секретный ключ неизвестен клиенту.

### Угроза 2: Кража токена через XSS
*   **Сценарий:** Внедрение JS-скрипта для кражи токена из `localStorage` или `document.cookie`.
*   **Мера защиты:** Оба токена хранятся в **`HttpOnly Cookie`**. JavaScript не имеет к ним доступа.

### Угроза 3: Компрометация Access Token (Кратковременная)
*   **Сценарий:** Перехват Access Token.
*   **Мера защиты:** Время жизни Access Token всего 15 минут. Даже при краже злоумышленник имеет доступ ограниченное время.

### Угроза 4: Разрастание Blacklist (DoS)
*   **Сценарий:** Атакующий многократно логинится и делает logout, забивая таблицу `token_blacklist`.
*   **Мера защиты:** Очистка Blacklist от токенов с истекшим `exp`. Rate limiting на `/login` и `/logout`.

---

## 3. От чего система НЕ ЗАЩИЩЕНА (Остаточные риски)
*Данные риски закрываются при развертывании системы в production-среде.*

### Угроза 5: Перехват токенов (MitM)
*   **Почему не защищены:** На этапе разработки используется протокол **HTTP без TLS**.
*   **Последствия:** Прослушивание трафика может привести к краже Cookie.
*   **Решение:** Использование **HTTPS/TLS** и установка флага `Secure` на Cookie.

### Угроза 6: Межсайтовая подделка запроса (CSRF)
*   **Почему не защищены:** Флаг `SameSite=Strict` временно отключен для работы на `localhost`.
*   **Последствия:** Теоретическая возможность отправки Cookie со стороннего сайта.
*   **Решение:** Включение флага `SameSite=Strict` при переходе на HTTPS.

### Угроза 7: Компрометация секретного ключа
*   **Почему не защищены:** Ключ `JWT_SECRET` захардкожен в исходном коде.
*   **Последствия:** Злоумышленник сможет подделать любой токен.
*   **Решение:** Хранение ключа в переменных окружения (`.env`), регулярная ротация.

### Угроза 8: Кража Refresh Token
*   **Почему не защищены:** Механизм Refresh Token будет реализован на следующем этапе (в текущей итерации только Access Token).
*   **Последствия:** При краже Refresh Token злоумышленник сможет долго обновлять Access Token (до 7 дней).
*   **Решение:** Хранение Refresh Token в БД для возможности его отзыва (Logout со всех устройств), короткое время жизни Access Token.
